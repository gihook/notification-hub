# Notification Hub

A small Django service that receives notifications over HTTP and routes them through RabbitMQ to separate Celery applications.

```
            POST /notifications/                     Celery messages
 client ───────────────────────────▶  hub  ───────────────────────────▶  RabbitMQ
        {"notification_id": "...",   (Django)   one message per target     │
         "data": {...}}                 │                                   │ queue: email
                                        │ looks up the id in                │ queue: analytics
                                        ▼ config/routing.json               │ queue: orders
                                  routing.json                              ▼
                                                                   Celery worker(s)
                                                                   consume chosen queues
```

## How it works

1. A client sends `POST /notifications/` with a JSON body that contains a string `notification_id` and any `data`.
2. The hub looks up the id in `config/routing.json`. Unknown ids are rejected with 404.
3. For every target listed for that id, the hub publishes one Celery message (`send_task`) to the target's **queue**, using the target's **task name**.
4. Any Celery app whose worker consumes that queue (`-Q <queue>`) and defines a task with that name processes the message. The task gets these keyword arguments:

   | kwarg             | description                                          |
   |-------------------|------------------------------------------------------|
   | `event_id`        | UUID generated by the hub; the same for every target |
   | `notification_id` | the id that was posted                               |
   | `data`            | the `data` field from the request (any JSON)         |
   | `received_at`     | ISO-8601 UTC timestamp                               |

The hub only publishes messages. It has no database and runs no tasks. Queues are durable and messages are persistent, so a notification waits in RabbitMQ until a consumer picks it up.

## Routing config

`config/routing.json` is the single place that defines which notification ids exist and where they go:

```json
{
  "default_task": "notifications.handle",
  "routes": {
    "user.signup":   [{"queue": "email"}, {"queue": "analytics"}],
    "order.created": [{"queue": "orders", "task": "orders.process"}]
  }
}
```

- `routes` maps each `notification_id` to a non-empty list of targets.
- Each target has a `queue` and an optional `task`. The task defaults to `default_task`.
- If an id has several targets, the notification fans out: one message goes to each queue.
- The file is validated when the hub starts, so an invalid config stops it from starting. After editing it, run `docker compose restart hub`.

The landing page at <http://localhost:8000/> lists all configured notification ids and their targets.

## API

`POST /notifications/`

```bash
curl -X POST localhost:8000/notifications/ \
  -H 'Content-Type: application/json' \
  -d '{"notification_id": "user.signup", "data": {"user": 1}}'
# 202 {"id": "<event_id>", "queued_to": ["email", "analytics"]}
```

| status | meaning                                                          |
|--------|------------------------------------------------------------------|
| 202    | published to every queue listed in `queued_to`                   |
| 400    | body is not a JSON object, or `notification_id` is missing or not a string |
| 404    | `notification_id` is not in `routing.json`                       |
| 503    | publishing to RabbitMQ failed (`queued_to` lists the queues that succeeded first) |

## Running

```bash
cp .env.example .env
docker compose up --build
```

| service          | URL / port                                          |
|------------------|-----------------------------------------------------|
| hub              | <http://localhost:8000/>                            |
| RabbitMQ AMQP    | `localhost:5672`                                    |
| RabbitMQ UI      | <http://localhost:15672/> (guest / guest)           |
| example-worker   | consumes the `email` and `analytics` queues         |

If those host ports are already taken, override them with `HUB_PORT`, `RABBITMQ_PORT` and `RABBITMQ_UI_PORT`:

```bash
RABBITMQ_PORT=5673 RABBITMQ_UI_PORT=15673 docker compose up -d
```

Tests (`--no-deps` keeps the running RabbitMQ untouched):

```bash
docker compose run --rm --no-deps hub python manage.py test
```

## Adding a consumer app

1. Copy `workers/example/` to `workers/<name>/`.
2. In `worker.py`, name the task to match the target's `task` in `routing.json` (or `default_task`):
   ```python
   @app.task(name="orders.process")
   def process(event_id, notification_id, data, received_at):
       ...
   ```
3. In its `Dockerfile`, set `-Q` to the queue(s) it should consume, e.g. `-Q orders`.
4. Add a service for it to `docker-compose.yml`, like `example-worker`.

Notes:
- A worker drops any message whose task name it doesn't know. Every app consuming a queue must define every task name routed to that queue.
- Several workers on the **same** queue share the load: each message goes to only one of them. To have several apps receive the same notification, give each app its own queue and list all of those queues under the notification id.

## Project layout

```
config/routing.json          notification ids → queues/tasks
hub/                         Django project (publisher)
  hub/settings.py            env-driven settings, Celery config
  hub/celery.py              publisher-only Celery app
  notifications/routing.py   load + validate routing.json
  notifications/views.py     landing page + POST endpoint
  notifications/templates/   landing page template
  notifications/tests.py
workers/example/             template Celery consumer app
docker-compose.yml           rabbitmq, hub, example-worker
```
