# Notification Hub

A small Django service that receives notifications over HTTP and routes them through RabbitMQ to separate Celery applications.

```
            POST /notifications/                     Celery messages
 client ───────────────────────────▶  hub  ───────────────────────────▶  RabbitMQ
        {"notification_id": "...",   (Django)   one message per target     │
         "data": {...}}                 │                                   │ queue: email
                                        │ looks up the id in                │ queue: analytics
                                        ▼ config/routing.json               │ queue: orders
                                  routing.json                              ▼
                                                                   Celery worker(s)
                                                                   consume chosen queues
```

## How it works

1. A client sends `POST /notifications/` with a JSON body that contains a string `notification_id` and any `data`.
2. The hub looks up the id in `config/routing.json`. Unknown ids are rejected with 404.
3. For every target listed for that id, the hub publishes one Celery message (`send_task`) to the target's **queue**, using the target's **task name**.
4. Any Celery app whose worker consumes that queue (`-Q <queue>`) and defines a task with that name processes the message. The task gets these keyword arguments:

   | kwarg             | description                                          |
   |-------------------|------------------------------------------------------|
   | `event_id`        | UUID generated by the hub; the same for every target |
   | `notification_id` | the id that was posted                               |
   | `data`            | the `data` field from the request (any JSON)         |
   | `received_at`     | ISO-8601 UTC timestamp                               |

The hub only publishes messages. It has no database and runs no tasks. Queues are durable and messages are persistent, so a notification waits in RabbitMQ until a consumer picks it up.

## Routing config

`config/routing.json` is the single place that defines which notification ids exist and where they go:

```json
{
  "default_task": "notifications.handle",
  "routes": {
    "user.signup":   [{"queue": "email"}, {"queue": "analytics"}],
    "order.created": [{"queue": "orders", "task": "orders.process"}]
  }
}
```

- `routes` maps each `notification_id` to a non-empty list of targets.
- Each target has a `queue` and an optional `task`. The task defaults to `default_task`.
- If an id has several targets, the notification fans out: one message goes to each queue.
- The file is validated when the hub starts, so an invalid config stops it from starting. After editing it, run `docker compose restart hub`.

The landing page at <http://localhost:8000/> lists all configured notification ids and their targets.

## API

`POST /notifications/`

```bash
curl -X POST localhost:8000/notifications/ \
  -H 'Content-Type: application/json' \
  -d '{"notification_id": "user.signup", "data": {"user": 1}}'
# 202 {"id": "<event_id>", "queued_to": ["email", "analytics"]}
```

| status | meaning                                                          |
|--------|------------------------------------------------------------------|
| 202    | published to every queue listed in `queued_to`                   |
| 400    | body is not a JSON object, or `notification_id` is missing or not a string |
| 404    | `notification_id` is not in `routing.json`                       |
| 503    | publishing to RabbitMQ failed (`queued_to` lists the queues that succeeded first) |

## Running

```bash
cp .env.example .env
docker compose up --build
```

| service          | URL / port                                          |
|------------------|-----------------------------------------------------|
| hub              | <http://localhost:8000/>                            |
| RabbitMQ AMQP    | `localhost:5672`                                    |
| RabbitMQ UI      | <http://localhost:15672/> (guest / guest)           |
| example-worker   | consumes the `email` and `analytics` queues         |
| mailer-worker    | consumes the `mailer` queue (bin reminder emails)   |
| scheduler        | Celery Beat: daily 08:00 check that triggers the bin reminder |
| Mailpit          | <http://localhost:8025/> (catches all outgoing mail), SMTP `localhost:1025` |

The mailer worker and the scheduler need their own env files and a Google service account key:

```bash
cp workers/mailer/.env.example workers/mailer/.env
cp workers/scheduler/.env.example workers/scheduler/.env
# in .env: GOOGLE_CREDENTIALS_FILE=/path/to/credentials.json
```

If those host ports are already taken, override them with `HUB_PORT`, `RABBITMQ_PORT`, `RABBITMQ_UI_PORT`, `MAILPIT_UI_PORT` and `MAILPIT_SMTP_PORT`:

```bash
RABBITMQ_PORT=5673 RABBITMQ_UI_PORT=15673 docker compose up -d
```

Tests (`--no-deps` keeps the running RabbitMQ untouched):

```bash
docker compose run --rm --no-deps hub python manage.py test
docker compose run --rm --no-deps mailer-worker python -m unittest
docker compose run --rm --no-deps scheduler python -m unittest
```

## Deploying (Proxmox LXC)

Production uses the base compose file plus `docker-compose.prod.yml`. That file adds restart policies, RabbitMQ credentials and log size caps, and stops publishing AMQP. It also disables `example-worker` and `mailpit` (start them with `--profile dev`). It needs Docker Compose v2.24 or newer.

**1. Create the container** on Proxmox from the Debian 12 template:

- Unprivileged
- 1–2 vCPU, 1–2 GB RAM, 8–16 GB disk
- A fixed LAN IP
- "Start at boot" turned on

Docker needs nesting and keyctl. Run this on the Proxmox host, then restart the CT:

```bash
pct set <CTID> -features nesting=1,keyctl=1
```

**2. Install Docker** in the CT from Docker's apt repo (see docs.docker.com/engine/install/debian):

```bash
apt install -y ca-certificates curl git
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
echo "deb [signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/debian $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  > /etc/apt/sources.list.d/docker.list
apt update && apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
docker run --rm hello-world
```

**3. Get the code and the secrets.** None of the secrets are in git, so copy them in with `scp`:

```bash
git clone <repo-url> /opt/notification-hub && cd /opt/notification-hub
cp .env.example .env
cp workers/mailer/.env.example workers/mailer/.env
cp workers/scheduler/.env.example workers/scheduler/.env
mkdir -p secrets && chmod 700 secrets   # put google-credentials.json here
chmod 644 secrets/google-credentials.json   # workers run as a non-root user inside the container
```

- `.env` needs these values:
  - a random `DJANGO_SECRET_KEY`
  - `DJANGO_ALLOWED_HOSTS=<lxc-ip>,<hostname>`
  - `RABBITMQ_DEFAULT_USER` and `RABBITMQ_DEFAULT_PASS`
  - a `CELERY_BROKER_URL` that uses those same credentials
  - `GOOGLE_CREDENTIALS_FILE=./secrets/google-credentials.json`
- `workers/mailer/.env`: switch to the Gmail SMTP block (App Password).
- `workers/scheduler/.env`: the defaults work as they are.

**4. Start the stack, and update it later:**

```bash
alias dcp='docker compose -f docker-compose.yml -f docker-compose.prod.yml'
dcp up -d --build          # first start
git pull && dcp up -d --build   # update
dcp ps; dcp logs -f mailer-worker scheduler
```

Once it's running, the hub is at `http://<lxc-ip>:8000/` and the RabbitMQ UI at `http://<lxc-ip>:15672/` (log in with the new credentials). For backups, a Proxmox `vzdump` of the CT covers the queued messages and the secrets.

## Mailer: bin-change reminder

`workers/mailer/` is a Python port of `okrugiceva-24/mail-sender/index.js`. It handles the `okrugiceva.bin_reminder` notification:

1. Reads the tenant emails from the Google Sheet (`EMAILS_RANGE`, default `Stanari!C2:C100`).
2. Reads the name of the person responsible (`REPLACER_RANGE`, default `Glavna!A5`).
3. Sends one email to all tenants saying who is responsible today.

The task **always sends** when triggered; it doesn't check any date. The emitter decides when to send the notification; normally that's the [scheduler](#scheduler-daily-trigger). To send one by hand:

```bash
curl -X POST localhost:8000/notifications/ -H 'Content-Type: application/json' \
  -d '{"notification_id": "okrugiceva.bin_reminder"}'
```

`data` is ignored.

## Scheduler: daily trigger

`workers/scheduler/` is a producer: a Celery worker with Beat embedded (`celery worker -B`). Every day at **08:00 Europe/Belgrade** it:

1. Reads the scheduled date from the sheet (`REPLACER_DATE_RANGE`, default `Glavna!B5`, format `M/D/YYYY`).
2. If that date is today, posts `okrugiceva.bin_reminder` to the hub (`HUB_URL`). The hub routes it to the mailer as usual.

It goes through the hub's HTTP endpoint, so `routing.json` still decides where the notification ends up. Network errors, Google API errors and hub 5xx responses are retried up to 5 times with backoff. A hub 4xx (for example an unknown notification id) fails straight away, because it means the config is wrong.

Run the check by hand:

```bash
# real check against today's date
docker compose exec scheduler celery -A scheduler call scheduler.check_bin_reminder

# pretend today is another day (testing only)
docker compose exec scheduler celery -A scheduler call scheduler.check_bin_reminder \
  --kwargs '{"today_override": "2026-11-06"}'

docker compose logs -f scheduler   # shows "not due" or "triggered"
```

If the container is down at 08:00, that day's check is skipped; Beat doesn't catch up missed runs.

By default mail goes to **Mailpit**, which catches every email and shows it at <http://localhost:8025/>; nothing is delivered. For real delivery, set the Gmail SMTP settings in `workers/mailer/.env` (see the commented block in `.env.example`) using a Gmail App Password. SMTP connection errors are retried up to 5 times with backoff.

## Adding a consumer app

1. Copy `workers/example/` to `workers/<name>/`.
2. In `worker.py`, name the task to match the target's `task` in `routing.json` (or `default_task`):
   ```python
   @app.task(name="orders.process")
   def process(event_id, notification_id, data, received_at):
       ...
   ```
3. In its `Dockerfile`, set `-Q` to the queue(s) it should consume, e.g. `-Q orders`.
4. Add a service for it to `docker-compose.yml`, like `example-worker`.

Notes:
- A worker drops any message whose task name it doesn't know. Every app consuming a queue must define every task name routed to that queue.
- Several workers on the **same** queue share the load: each message goes to only one of them. To have several apps receive the same notification, give each app its own queue and list all of those queues under the notification id.

## Project layout

```
config/routing.json          notification ids → queues/tasks
hub/                         Django project (publisher)
  hub/settings.py            env-driven settings, Celery config
  hub/celery.py              publisher-only Celery app
  notifications/routing.py   load + validate routing.json
  notifications/views.py     landing page + POST endpoint
  notifications/templates/   landing page template
  notifications/tests.py
workers/example/             template Celery consumer app
workers/mailer/              bin reminder mailer (Google Sheets + SMTP)
workers/scheduler/           Celery Beat producer: daily date check -> posts the notification
docker-compose.yml           rabbitmq, hub, example-worker, mailer-worker, scheduler, mailpit
docker-compose.prod.yml      production override (restart, creds, no AMQP/mailpit/example)
```
